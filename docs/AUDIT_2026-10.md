## Contexto del sistema
- **Qué hace:** marketplace de delivery para Tinogasta (Catamarca): tiendas publican productos, clientes piden, repartidores entregan; pago digital por MercadoPago; el admin aprueba cuentas y libera la plata (principio: el dinero nunca sale solo).
- **Backend:** Next.js 14 App Router (34 rutas API en `src/app/api`) + Firebase Admin SDK; lógica en `src/lib` (`money.ts` única fuente del reparto, `payout-service`, `stock-service`, `notify-server`, `reconcile-mp`, `approval-service`).
- **Frontend:** Next.js 14 + React, Tailwind + shadcn/ui, Leaflet (mapas), Recharts (analíticas), 43 páginas; PWA instalable + APK (TWA).
- **Base de datos:** Firestore (24 colecciones + `order_private`, `order_idempotency`), Firebase Auth, Storage, FCM. Reglas: `firestore.rules` (~520 líneas), `storage.rules`.
- **Infra:** Vercel Hobby (2 crons: conciliación MP 13:30 UTC y liquidación 14:00 UTC), Sentry, backups diarios de Firestore (7 días).
- **Roles:** `buyer`, `store`, `delivery`, `admin` (`roles_admin/{uid}` con nivel `full`/`support`).
- **Tráfico:** hoy una prueba con pocos testers; **esperado a 1 año: ~50-200 pedidos/día** (decisión de David para esta auditoría), decenas de tiendas, miles de usuarios, pocos repartidores.

**ARQ-003 · Un repartidor puede "des-entregar" su propio pedido terminado** · backend/reglas · **Alta** · CONFIRMADO (estático)

Test: ataque (Entregado → 'En reparto' ❌) + regresión ('En camino' → 'En reparto' ✅) en la misma corrida. Fix de raíz más amplio: tabla única de transiciones `src/lib/order-state.ts` usada por las 6 rutas y las reglas; y mover 'En reparto'/'Listo para recoger' (hoy `updateDoc` directo con avisos lanzados desde el navegador, `delivery-orders-view.tsx:229-255`, `order-service.ts:170`) a una API con `notifyUser` server-side — si el repartidor cierra la pestaña en ese instante, el comprador no se entera.

**ARQ-007 · El aviso "¡Llegamos!" se pierde de forma intermitente** · backend · **Alta** · CONFIRMADO
`src/app/api/orders/confirm-delivery/route.ts:116,126`: los dos `notifyUser(...)` van **sin `await`** y la ruta responde en `:136`. En Vercel la función puede congelarse al responder → el push al comprador (el que dispara calificar y la ventana de reclamo) y el de la tienda salen "a veces". Único sitio con este patrón. **ARQ-006 · `confirm-stock` sin transacción: puede resucitar un pedido cancelado** · backend · **Alta** · CONFIRMADO (es BUG-202 con el escenario grave)
`confirm-stock/route.ts:61-72` lee y valida `'Pendiente de Confirmación'`, hace ~N lecturas de catálogo y escribe en `:157` con `orderRef.update` (0 `runTransaction`). `cancel` sí es transaccional y devuelve stock. Carrera: el comprador cancela mientras la tienda confirma → `confirm-stock` pisa `'Cancelado'` con `'Pendiente de Pago'`: pedido resucitado con el stock ya devuelto, y `/api/checkout` lo deja pagar. Solución: envolver la escritura en `adminDb.runTransaction(async tx => { const fresh = await tx.get(orderRef); if (fresh.data()!.status !== 'Pendiente de Confirmación') throw new Error('__STATE_CHANGED__'); tx.update(orderRef, {...}); })` → 409. Las lecturas de catálogo quedan afuera. Test: `Promise.all([confirmStock, cancel])` → termina `Cancelado` o `Pendiente de Pago`, nunca `Pendiente de Pago` con `stockReturnedAt`.

**ARQ-004 · Sesión vencida o usuario deshabilitado: ningún camino lo maneja** · frontend-auth · **Alta** · CONFIRMADO
`src/lib/authed-fetch.ts`: `await user.getIdToken()` sin try/catch y no mira `res.status`; los 36 llamadores tratan 401/403 como un toast genérico; `auth-context.tsx:129` usa `onAuthStateChanged` (no `onIdTokenChanged`); no hay logout automático ni `middleware.ts`. Qué pasa: un usuario borrado/deshabilitado desde el admin sigue navegando ~1h con el perfil en memoria; al refrescar el token, `getIdToken()` lanza `auth/user-token-expired`/`user-disabled` → mensaje crudo en inglés y app "zombi" (listeners denegados y tragados = pantallas "sin pedidos"). Caso típico: el APK días en segundo plano. Solución (3 piezas):
```ts
// authed-fetch.ts
export class SessionExpiredError extends Error {}
export async function authedFetch(url: string, user: User | null, body: unknown) {
  let token: string | null = null;
  try { token = user ? await user.getIdToken() : null; }
  catch (e: any) {
    if (/user-token-expired|user-disabled|user-not-found/.test(e?.code ?? "")) { await signOut(auth); throw new SessionExpiredError(); }
    throw e;
  }
  const res = await fetch(url, { method: "POST", headers: { "Content-Type": "application/json", ...(token ? { Authorization: `Bearer ${token}` } : {}) }, body: JSON.stringify(body) });
  if (res.status === 401) { await signOut(auth); throw new SessionExpiredError(); }
  return res;
}
```
+ `onIdTokenChanged` en auth-context y, si el `onSnapshot` del perfil da `permission-denied` con usuario presente → `currentUser.reload().catch(() => signOut(auth))`; + un `useEffect` en `app-content.tsx` que ante `SessionExpiredError` (o `user` que pasa de existir a `null`) haga `router.replace('/login?expired=1')` + toast "Tu sesión venció". Los 6 `fetch` crudos (`pending-list:52,72`, `delivery-personnel-list:69`, `admin/users:97`, `profile:110`, `order-service:145`) pasan a `authedFetch`. **A confirmar en vivo:** el agente de ciclos está probando la revocación de tokens.

## Resumen ejecutivo

**El sistema está sano para la escala de hoy y el núcleo del negocio funciona de punta a punta.** La regresión contra producción dio 201 verificaciones OK y 0 fallas de código; los 15 fixes de las auditorías anteriores siguen vigentes; el ciclo completo (registro × 3 roles → pedido → pago → take → PIN → reseñas → reclamo → reembolso → retiro) se ejecutó por la UI y la API reales con ground truth en cada paso, y la plata cuadra con `money.ts` al peso. Ningún hallazgo nuevo mueve plata mal ni expone datos a anónimos.

**Lo que esta auditoría agrega son tres cosas que las anteriores no miraban:**
1. **Escala (2 Críticas, ambas de rendimiento, no de seguridad):** el panel del repartidor y el de la tienda escuchan TODO su historial de pedidos sin estado ni límite. Hoy son decenas de docs; a 50-200 pedidos/día son miles en memoria del celular en cada apertura → es lo primero que rompe la app en un Android de gama baja, y mucho antes de que duela en la factura. Arreglo chico (acotar las consultas por estado + paginar el historial). En la misma familia: la conciliación con MercadoPago **ya muere en silencio a ~7 pedidos/día** por `payment.get` secuencial contra un `maxDuration` de 60 s.
2. **Sesión vencida y operador sin red de validación (Altas de frontend):** nada maneja un token vencido o un usuario deshabilitado (el APK en segundo plano >1 h muestra "No autorizado" crudo); `/admin/settings` y `/my-store/edit` guardan tarifas negativas, comisión 150 %, tiendas sin nombre y horarios invertidos; el perfil del repartidor usa otros valores de vehículo que el alta y pisa el dato que decide qué documentos son obligatorios; el checkout y el carrito en celular esconden el total; `/terms` y `/privacy` son una pared de texto; un cliente nuevo vería "Hola, Invitado".
3. **Backend: 3 huecos concretos y una deuda estructural:** un repartidor puede "des-entregar" su pedido terminado por una regla sin guard de estado previo; `confirm-stock` sin transacción puede resucitar un pedido cancelado; el aviso "¡Llegamos!" se pierde a veces por dos `notifyUser` sin `await`. La deuda: avisos copiados 13 veces (por eso hay avisos que no salen), máquina de estados del pedido en 4 lugares, dos capas de Firebase, `strictNullChecks` apagado (raíz de 119 `as any`).

**Dependencias:** `npm audit` subió de 15 a 38 vulnerabilidades con 2 RCE críticas en `next@14.2.35`; no existe ningún 14.2.x posterior, el fix es Next 16 (salto mayor, decisión aparte). **Infra:** Vercel Hobby prohíbe uso comercial y ya no quedan crons libres → Pro al lanzar.

**Totales:** 2 Críticas · 24 Altas · 42 Medias · ~43 Bajas (109 hallazgos, ~25 de ellos solapados entre frentes y marcados como tales). Las dos Críticas y 10 de las 24 Altas se arreglan en menos de un día de trabajo total.

## Recomendaciones de escalabilidad (50-200 pedidos/día)

- **Regla única que cubre casi todo:** ninguna pantalla escucha historial. En vivo = estados activos acotados; historial = paginado bajo demanda; totales = aggregations o acumuladores. Hoy la rompen 6 pantallas (PERF-001/002/005) y es la diferencia entre ~40 k y ~200 k lecturas/mes al año a 50/día.
- **Costo proyectado con el código actual:** 50/día ≈ cuota gratis el mes 1 y ~4× al año; 200/día ≈ US$18-20/mes creciendo 16-18× por el historial acumulado. Con Tanda 0 + PERF-004/005 el crecimiento queda plano (el costo deja de depender del historial).
- **GPS es el 75-90 % del costo por pedido:** throttle a 10 s/50 m y un subdocumento propio; el tracking en segundo plano llegará con la app nativa, no conviene optimizar más que eso en web.
- **Procesos batch (conciliación, liquidación, pasivo):** paralelizar en tandas, `maxDuration` explícito, escribir el registro de corrida al inicio; con acumuladores por cuenta dejan de ser O(pedidos). Son los que se rompen sin que nadie vea nada.
- **Vercel Pro + Firestore Blaze con alertas de presupuesto** (US$10/mes de umbral) antes del lanzamiento; TTL de Firestore en `notifications` y `reconciliations` (PERF-019).
- **Qué NO hacer todavía:** Cloud Functions, Upstash para el rate limit, servicio de routing, `stats/platform` global, CSP estricta — cada uno recién cuando su número lo pida (anotado en cada hallazgo).
- **Qué se rompe primero a 10× (2.000/día):** paneles de repartidor/tienda → conciliación MP → dashboard/Finanzas → saldos O(n) → factura del GPS → límites de Vercel. El orden del plan sigue exactamente esa lista.
